# The API and sync

How the API checks who is calling, how it keeps records and photos, and how a device syncs with it. The rules in `CLAUDE.md` apply too.

- Clerk's session tokens are checked by ASP.NET Core's JWT bearer authentication in `Auth/ClerkAuthentication.cs`. Clerk stays behind that file and the `ClerkUserId` column on `Person`. Everything else points at our own `Person.Id`, so the sign-in service can be replaced.
- Never take the caller's identity from the request body or the URL. `CurrentPerson` finds them from the token.
- Anything under `/collections/{collectionId}` needs `CollectionPolicies.View` or `CollectionPolicies.Edit`. The policy checks the caller's membership on every request, so a viewer can't change data even with a modified app.
- `docker compose up --build` runs the API on port 5180 with SQL Server, and Azurite in place of Blob Storage. It applies its migrations on start, locally and hosted. A new migration is made with `dotnet tool restore`, then `dotnet ef migrations add <Name> --project src/Stikling.Api --output-dir Data/Migrations`.
- Each signed-in person can send a burst of 1000 requests, and 600 a minute after that (`RequestLimits`, in `Auth/RequestLimits.cs`). Past that the API answers 429 with `Retry-After`. Photo transfers in `StiklingApi` wait and try again, and anything else ends the sync with a message until the next one. Requests without a sign-in aren't limited, apart from the share pages and the plant facts below, which have a limit per address. The health check isn't limited.
- Records from the app are kept as their JSON in one `Records` table, keyed by collection, kind and id. The server only reads the id, `updatedAt` and `deletedAt`, so a new field in a model needs no migration. The newest `updatedAt` wins, and each accepted change gets the collection's next change number, which is what devices fetch by. The person's `UserSettings` are kept the same way in `PersonSettings`. A record the server can't keep, like one dated more than a day ahead of its clock, is refused on its own, and the rest of the upload is kept.
- Share links (`Sharing/`) are the only pages anyone can open without signing in. `GET /s/{token}` writes a plain HTML page for one plant or propagation, and `GET /s/{token}/photos/{photoId}/{size}` serves its images. On `share.stikling.app` the same pages are at `/{token}`, because `ShareHost` moves the path under `/s` before routing. The `ShareLinks` table is on the server only and isn't a synced record: it has a token (16 random bytes, base64url), the collection, the plant or propagation, whether notes show, a name and a line, the photos left out, and a time zone. The app turns a link on, changes it and turns it off through `/collections/{collectionId}/shares`, which needs `Edit` to change anything. A plant has one link that is on at a time, at most 50 are on in a collection and one person can make 20 a day (`ShareLinkRules`). A link that is turned off keeps its row, so its address answers 410 for good, and turning sharing on again makes a new token. What is public is decided in Core's `SharePage`, which gets the records and says what the page shows. The API only finds the records (photos and timeline entries by `JSON_VALUE` on `subjectId`, so a view doesn't read the whole collection) and writes them out as HTML in a Razor component, with no JavaScript. A plant's page also reads the propagation it was potted up from (`FromPropagationId`): its photos and entries, by `subjectId`, up to the day it was potted up (`SharePage.RootingPhotos` and the cut-off in `SharePage`), and the photo endpoint serves those photos too, by the same rule. Anonymous requests to `/s/` get a bucket per address (`RequestLimits:PublicBurst` 300 and `RequestLimits:PublicPerMinute` 300), with the address read from `X-Forwarded-For` as the ingress adds it. When a plant or propagation arrives deleted in a push, its link is turned off in the same transaction, so a restore never brings the page back. Deleting a collection deletes its links. The page is sent with `Cache-Control: no-cache` and its images with five minutes, so turning a link off or hiding notes shows within minutes. `GET /s/{token}/copy` returns the same page as JSON (`ShareCopy`, with enums as text), for someone who was given the plant to keep its history in their own app. It is built from the `SharePageModel` and the subject, so it never says more than the page, and it answers 404 unless the plant has left (given away or sold) or units of the propagation were given away (`SharePageModel.CanKeep`). It is sent with `Cache-Control: no-cache`, and the default CORS policy and the per-address limit apply to it like the rest of `/s/`. The page shows a button for it when `CanKeep`, which opens `{Share:AppUrl}received/{token}` in the app (`Share:AppUrl`, `https://stikling.app/` unless set, `http://localhost:5170/` in Development). A page also reads the `receivedHistories` of the subject and of the propagation a plant came from, by `subjectId`, and `SharePage` puts their items before the subject's own. The photos copied with a history are ordinary photos of the subject (`ReceivedHistoryId` set), so the photo endpoint serves them by the same rules. A change here needs a look at `SharePage` first, since anything it doesn't name is left off the page.
- The public collection page (`Sharing/PublicPage*`) is the second thing anyone can open without signing in: one page for a whole collection, with its plants as a gallery of cover photos and names, and optionally its cuttings, what is up for swap, the wishlist and a story for each plant or cutting. Like share links it is plain HTML with no JavaScript, written by Razor components (`PublicPageView`, `PublicPartView`, `PublicStoryView`, styled by `PublicPageStyles` on top of `ShareStyles`). Two tables, on the server only and not synced records. `PublicPages` has a row per page: a token (16 random bytes, base64url, as for share links), the collection (deleted with it), the title and line, the layout (`Shelves`, `LongPage`, `PhotoWall`) and order (`Newest`, `Name`) as text, the switches `ShowPropagations` (on from the start), `ShowSwap`, `ShowWishlist`, `ShowStories` and `Searchable`, the language (`en` or `da`), a time zone, and `NameClaims`, a JSON list of when the name was last changed (only the last 24 hours are kept). A collection has one page that is on, enforced by a filtered unique index on `CollectionId` where `TurnedOffAt` is null. `PublicPageNames` has one column, `NameHash`, the SHA-256 of a name as 64 hex characters, and a row is added when a name is claimed and never deleted, not even when the account or the collection goes (the cascade only removes `PublicPages`). That is what keeps a name from being taken again after the person's own data is erased, and nothing in it points at a person or a collection. The app changes the page through `/collections/{collectionId}/public-page` (`PublicPageEndpoints`), which follows `ShareLinkEndpoints` (a transaction with `LockCollectionAsync`, `Edit` to change anything): `GET` the live page or 404, `POST` turns it on (503 without `Share:BaseUrl`, the live page again if there is one, 429 after 5 turned on by one person in a day, 201 with a new token), `PUT` replaces the settings (400 for a title over 80 or a line over 200 characters), `DELETE` turns it off (`TurnedOffAt` set, the name given up, the row kept so the token answers 410 for good, and turning it on again makes a new token). `PUT /name` takes the name through `PublicPageRules.NormalizeName` and `CheckName` (3 to 30 characters of a to z, 0 to 9 and hyphens, not starting or ending with one or having two in a row, nothing reserved or starting with `stikling`): a bad name is 400 with the `NameProblem` as text in `extensions["problem"]` so the app can use its own words, the same name as now is 200, a name whose hash is in `PublicPageNames` is 409 whether it is in use or was given up (the answer never says which), a page that changed its name 3 times in 24 hours gets 429, and otherwise the hash is inserted, the name set and 200 returned (a race on the hash is 409 too). A null name gives the name up: the hash stays, so the old address answers 410. A name is only ever used once, by anyone, including the page that had it. The pages live in the same `/s` group as share pages, so the same security headers and per-address limit apply, and `ShareHost` needed no change since `/@name` is moved under `/s` like a token. An address is `@name` or a token: `/s/{token}` and `/s/{token}/photos/...` look for a share link first and hand over to the public page when there is none, and a name is looked up in lower case among live pages, with 410 when its hash exists and 404 when it doesn't. Under an address are the front page, `/plants`, `/cuttings`, `/swap` and `/wishlist` (48 tiles or 100 wishlist lines a page, `?page=n`, a bad or out of range n is 404, a part that is off is 404), the stories at `/plants/{id}` and `/cuttings/{id}` (404 unless stories are on and the subject shows) and `/photos/{photoId}/{size}`. What is public is decided in Core's `PublicCollectionPage`, the way `SharePage` does it for share links, and anything it doesn't name is left off: plants that are active, not deleted, not hidden (`HiddenFromPublicPage` on `Plant`, `Propagation` and `Photo`, set from the app through the repositories so it syncs) and not the example family; cuttings that are still going, not hidden, and only while that part is on; photos that are not reference photos, not hidden and have an image on the server; wishes by name only, never prices, where to find them or notes; the swap part from `SwapLists.Build` over what shows. A story is `SharePage` with notes off, hidden photos left out (rooting photos too), the parent only if it shows, the rooting only if it is not hidden, hidden cuttings removed and no way to keep the history. `PublicCollectionPage.ServesPhoto` decides which photos the photo endpoint serves: a cover of a tile that shows, or with stories on a photo on a story that shows, rooting photos included. The API reads the collection's plants, cuttings and (with the wishlist on) wishes by `Kind`, and the photos of only the subjects being drawn in one query (`JSON_VALUE` on `subjectId` against `OPENJSON` of the ids, next to `ByPropertyAsync`), and leaves out photos whose image hasn't arrived. Pages are sent `Cache-Control: no-cache` and images five minutes. Every response carries `X-Robots-Tag: noindex, nofollow` and a robots meta tag unless `Searchable` is on, and a page with a name carries `<link rel="canonical">` to its `@name` address on every page. `GET /s/robots.txt` (the share host's `/robots.txt`) allows everything and names `/sitemap.xml`, and `GET /s/sitemap.xml` lists the searchable live pages with their parts, numbered pages and, with stories on, every story, up to 50,000 urls, with `lastmod` and `Cache-Control: public, max-age=3600`. A page is written in its own language, not the visitor's: the handler sets the culture while it works with Core, and a small `IResult` sets it again before the component renders, since `RazorComponentResult` runs after the handler has returned. The text is in Core's `PublicPage` resource files and reaches the views through the public `PublicPageText`, since Core's resource classes are internal. Share links stay English and unchanged. The export ZIP has the collection's pages as `publicPages.json`, without `NameClaims`.
- Notifications (`Notifications/`) send one push notification a day with what Today asks for, and never watering. The server only sends text the device made: the app works out the text for up to 31 days with Core's `TodayNotice.Days` and uploads it, so the server never looks at a person's records. Two tables, on the server only and not synced records. `PushSubscriptions` has a row per device: the Web Push endpoint, its keys and at most 10 per person, where the 11th removes the oldest. The endpoint is found by `EndpointHash`, a SHA-256 of it, since it is too long for an index. `NotificationSchedules` has a row per person: the time zone, the time of day on a quarter hour, the days as `DaysJson`, `LastSentOn`, and `NextSendAt`, the UTC moment of the next day with text, recomputed on every upload and after every send or skip. Both go with the person when the account is deleted. The endpoints are `GET /notifications/key` (the VAPID public key, no sign-in, 404 without keys) and under `/me/notifications` `PUT /subscriptions` (an endpoint held by another person moves to the caller), `POST /subscriptions/remove`, `PUT /days` (replaces the schedule, and `notifyAt: null` turns it off: the row stays with no days and no next send, so `LastSentOn` still stops today being sent twice when it is turned on again) and `POST /test` (sends a test to the caller's own endpoint, 410 and the row deleted if the push service says it is gone, 502 if it fails). They answer 503 when no keys are set. Sending is a Container Apps job: the API's image started every 15 minutes with `send-notifications` (`NotificationJob`, a plain host that never applies migrations). `NotificationSender` reads the schedules with `NextSendAt` in the past and sends the day's text to each of the person's devices. A day more than 2 hours past its time is skipped, so a stopped job doesn't send an old list in the evening. A subscription the push service answers 404 or 410 for is deleted. Sending goes through `IPushSender` (Lib.Net.Http.WebPush, standard Web Push with VAPID, no paid service), which the tests replace with a fake. To run it locally, make keys with `npx web-push generate-vapid-keys --json` and set `Notifications:VapidPublicKey` and `Notifications:VapidPrivateKey` with `dotnet user-secrets`, or as env in docker compose from an uncommitted `.env`. Without keys the endpoints answer 503. `dotnet run --project src/Stikling.Api -- send-notifications` runs the sender once. The Azure side, and how to turn it on, is in `docs/ops/hosting.md`.
- Plant identification (`Identification/`) names the plant in a photo through Pl@ntNet, for the app when a person is signed in and has no Pl@ntNet key of their own on the device (with one, the app calls Pl@ntNet itself from `identify.js`, and the API isn't involved). `POST /identify` takes a multipart `image` (a JPEG or PNG by its first bytes, at most 10 MB, else 400) and an optional `lang` (`da` or `en`), needs a sign-in, and answers 503 without `Identification:PlantNetApiKey`. It answers `IdentificationResponse` (Core) with up to 5 suggestions, in the same shape the app builds from Pl@ntNet's own answer (`PlantNetResults`, the one place that reads it). Pl@ntNet's 404 is a 200 with an empty list. A 429 problem says whose limit it is in `reason`: `person` after `DailyLimitPerPerson` (10) a day, `total` after `DailyLimitTotal` (500, Pl@ntNet's free allowance) across everyone, or when Pl@ntNet itself answers 429. A failure at Pl@ntNet is a 502. Uses are counted in `IdentificationUses` (person and UTC day, since Pl@ntNet's quota restarts at midnight UTC) after a 200 or 404, rows older than yesterday are deleted on each call, and the table goes with the person. It is on the server only, not a synced record, and not in the export. The photo is passed on and never stored or logged. Pl@ntNet takes its key in the address, so `PlantNetIdentifier` logs only the status it got, its HTTP client has no logging (`RemoveAllLoggers`), and Sentry drops breadcrumbs about it and doesn't report failed requests. The tests replace `IPlantIdentifier` with a fake. To run it locally, get a key at my.plantnet.org and `dotnet user-secrets set Identification:PlantNetApiKey <key> --project src/Stikling.Api` (or `Identification__PlantNetApiKey` in an uncommitted `.env` for docker compose). The Azure side is in `docs/ops/hosting.md`.
- Photo images don't travel with the records. After the records, `PhotoSyncService` in `Core/Sync` sends the images from the `photoUploads` list in `db.js` and fetches thumbnails for the `photoDownloads` list. `db.js` keeps both lists in the same transaction as the images. Full sizes are only fetched when a photo is opened. The API keeps each image as a blob, with a `PhotoImages` row so a collection's photo space (1 GB, `Photos:MaxBytesPerCollection`) can be added up, and deletes the images when a photo's record arrives deleted.
- The sync logic on the device side is `SyncService` in `Core/Sync`, tested against `FakeSyncStore` and `FakeSyncServer`. `SyncRecord`, `PushRequest` and the other request formats there are shared with the API.
- In the app, `SyncRunner` decides when to sync, and `IndexedDbSyncStore` is the device side of it. Every write in `db.js` also puts the record on the change list, the `changes` store, in the same transaction. That covers every store except the ones in `NOT_RECORDS`, the stores that don't hold records, like `photoBlobs`.
- `db.js` keeps the fields of a stored record that the app didn't send when saving it, so a device on an older version can't erase a field that a newer version added. Only fields at the top of the record are kept this way.
- Settings that differ between local and hosted (the Clerk instance, the app's origins, the connection string) are in `appsettings.Development.json` locally, and in the container's environment in `infra/resources.bicep` when hosted. `Sentry__Dsn` is one of them: empty locally and in the tests, so nothing is sent, and set from `sentryDsn` in `infra/main.bicepparam` when hosted. Secrets never go in the repo, and the hosted API has one: the VAPID private key for notifications, a secret in its Key Vault that the container reads through its managed identity (`Notifications__VapidPrivateKey`). The same identity reaches the database and storage.
- The plant facts card (`PlantFacts/`) answers `GET /plant-facts?genus=&species=&language=` without a sign-in, with `PlantFacts(Summary, Facts)` from Core: the Wikipedia summary (`IWikipediaSource`, the REST page summary, Danish first and English when Danish has none, a genus page only if it is about a genus or a plant) and a few Trefle facts (`ITrefleSource`, species only, and only when `PlantFacts:TrefleToken` is set). Both are `AddHttpClient` clients with a 10 second timeout, and the tests replace them with fakes. The parsing is in Core (`WikipediaParser`, `TrefleParser`). Names must be letters, hyphens, × or spaces, at most 60 characters, or it answers 400. It answers 200 with both parts null when nothing is found, and 502 only when Wikipedia failed and Trefle has nothing. Answers are cached in the server's memory (`PlantFactsService`, 5000 entries): 7 days when something was found, 1 day when not, and 5 minutes when a source failed, so a source that is down isn't asked again by every request. A complete answer has `Cache-Control: public, max-age=86400`, and one with a gap from a failed source has `no-store`. Anonymous requests get a bucket per address under the key `facts-ip:`, with its own limit (`RequestLimits:FactsBurst` 30 and `RequestLimits:FactsPerMinute` 30), lower than the share pages'. From Trefle only the height, bloom months, growth habit and sources are read, and never edibility, toxicity, light, humidity, soil or anything else that sounds like care, since its own issues call these unreliable and the app never gives care advice from an outside source. Trefle takes its token in the address, so the clients have no request logging (`RemoveAllLoggers`), only status codes are logged, and `ErrorReporting` drops Sentry's breadcrumbs for outgoing requests. To run it locally: `dotnet user-secrets set PlantFacts:TrefleToken <token> --project src/Stikling.Api`; without one the card is Wikipedia only. Hosted, the token is the `trefle-token` secret, see `docs/ops/hosting.md`.
